## 🔴 Blocker 1 — release builds are signed with the debug key

`android/app/build.gradle:112-115`:
```gradle
release {
    // Caution! In production, you need to generate your own keystore file.
    // see https://reactnative.dev/docs/signed-apk-android.
    signingConfig signingConfigs.debug
    ...
}
```
This is the untouched React Native template default — its own comment flags it. Right now a "release" build is signed with `android/app/debug.keystore` (the well-known, shared debug key — fine for local `debug` builds, not fine for what you upload to Play).

**Why this matters more than a normal bug:** whatever key you first upload an AAB signed with (or enroll into Play App Signing with) is tied to this `applicationId` close to permanently — fixing it after the fact requires a Google support case, not a code change. Get this right before the first upload, not after.

Note: `android/app/debug.keystore` being committed to git is **normal and intentional** — check `taybat_app/.gitignore`, it has `*.keystore` with an explicit `!debug.keystore` exception. The gitignore already correctly protects against a *real* release keystore being committed. The only actual problem is that `signingConfig signingConfigs.debug` line.

### Fix — recommended: let EAS manage the release keystore
Since `android/` isn't regenerated by `expo prebuild` here, EAS's usual automatic credential wiring (which normally patches gradle files during prebuild) won't kick in on its own — the gradle file has to be told where to look. Do both of these:

**1. Add a real `release` signingConfig that reads from Gradle properties:**
```gradle
signingConfigs {
    debug {
        storeFile file('debug.keystore')
        storePassword 'android'
        keyAlias 'androiddebugkey'
        keyPassword 'android'
    }
    release {
        if (project.hasProperty('MYAPP_UPLOAD_STORE_FILE')) {
            storeFile file(MYAPP_UPLOAD_STORE_FILE)
            storePassword MYAPP_UPLOAD_STORE_PASSWORD
            keyAlias MYAPP_UPLOAD_KEY_ALIAS
            keyPassword MYAPP_UPLOAD_KEY_PASSWORD
        } else {
            // local dev fallback only — EAS Build injects the real values above
            storeFile file('debug.keystore')
            storePassword 'android'
            keyAlias 'androiddebugkey'
            keyPassword 'android'
        }
    }
}
buildTypes {
    debug {
        signingConfig signingConfigs.debug
    }
    release {
        signingConfig signingConfigs.release
        // ...unchanged (shrinkResources / minifyEnabled / proguardFiles / crunchPngs)
    }
}
```

**2. Generate/register the keystore with EAS and let it inject those properties at build time:**
```bash
cd taybat_app
eas credentials
# → Android → production → Set up a new keystore → let EAS generate one
```
EAS stores it server-side and injects `MYAPP_UPLOAD_STORE_FILE`/`_STORE_PASSWORD`/`_KEY_ALIAS`/`_KEY_PASSWORD`-equivalent values into the build environment automatically for builds run via `eas build`. You never see or handle the keystore file yourself, and it can't leak into the repo.

**Alternative (manual key, more control, more responsibility):**
```bash
keytool -genkeypair -v -storetype PKCS12 \
  -keystore taybat-release.keystore -alias taybat-upload \
  -keyalg RSA -keysize 2048 -validity 10000
```
Then either commit its path/passwords to `android/gradle.properties` (gitignored — add `gradle.properties` line, or better use `~/.gradle/gradle.properties` outside the repo entirely) or run `eas credentials` → import an existing keystore so EAS still injects it during CI builds. **Back this keystore up somewhere durable and outside git regardless** — losing it permanently blocks future updates to this exact `applicationId`.

## 🔴 Blocker 2 — Google Sign-In has no production Android OAuth client

`android/app/google-services.json` has **zero `oauth_client` entries** for `com.tayabat.sys` (checked directly, not assumed). Without one tied to your release signing certificate's SHA-1, `@react-native-google-signin/google-signin` will fail to authenticate in any real release build, even though it may appear to work in Expo Go / dev client (those use a different, already-registered debug SHA-1).

### Fix (do this *after* Blocker 1 — you need the real release keystore's SHA-1 first)
1. Get the release keystore's SHA-1:
   ```bash
   eas credentials   # Android → production → view keystore → copy SHA-1
   # or, for a manually generated keystore:
   keytool -list -v -keystore taybat-release.keystore -alias taybat-upload
   ```
2. Firebase Console → Project `al-tayabatcom-123b4` → Project settings → Your apps → `com.tayabat.sys` (Android) → Add fingerprint → paste the SHA-1.
3. Google Cloud Console (same project) → APIs & Services → Credentials → confirm an **Android** OAuth client now exists for this package + SHA-1 (Firebase usually creates it automatically once the fingerprint is added).
4. Firebase Console → download the updated `google-services.json` → replace **both** `taybat_app/google-services.json` (referenced by `app.json`) and `taybat_app/android/app/google-services.json` (the committed native copy — since `android/` isn't regenerated by prebuild here, the stale copy under `android/app/` won't auto-update on its own).
5. Also note: `app.json`'s Google Sign-In plugin config still has a literal placeholder —
   ```json
   "iosUrlScheme": "com.googleusercontent.apps.REPLACE_WITH_YOUR_REVERSED_IOS_CLIENT_ID"
   ```
   Not a Play Store blocker (iOS-only), but it's clearly unfinished — fix before an iOS release.

## eas.json — production profile needs a few explicit settings

Currently `"production": {}` relies entirely on defaults. Make it explicit so builds are reproducible and versioning doesn't need manual gradle edits per release:

```json
{
  "cli": {
    "version": ">= 15.0.0",
    "appVersionSource": "remote"
  },
  "build": {
    "development": { "developmentClient": true, "distribution": "internal" },
    "preview": { "distribution": "internal" },
    "production": {
      "android": {
        "buildType": "app-bundle",
        "autoIncrement": true
      }
    }
  },
  "submit": {
    "production": {
      "android": {
        "serviceAccountKeyPath": "./google-play-service-account.json",
        "track": "internal"
      }
    }
  }
}
```
- `buildType: app-bundle` — Play Store requires an `.aab`, not an `.apk`, for new apps.
- `appVersionSource: remote` + `autoIncrement: true` — EAS bumps `versionCode` automatically per build instead of hand-editing `android/app/build.gradle:95` before every release.
- `submit.production` — needed for `eas submit` (see below); the JSON key path must be gitignored (add `google-play-service-account.json` to `taybat_app/.gitignore` before creating the file).

## Google Play Console — one-time app setup

If there's no Play Console app entry yet:
1. [play.google.com/console](https://play.google.com/console) → pay the one-time $25 developer registration fee if this account hasn't done it before.
2. Create app → name "الطيبات" → default language Arabic → App (not game) → Free.
3. Before **any** release track can go out, Play Console requires these sections complete under "Set up your app" / "App content":
   - **Privacy policy URL** — ✅ ready: `https://al-tayabat.com/privacy`
   - **Account deletion URL** — Play Console has a dedicated field for this (separate from the general privacy policy, required since the account-deletion policy took effect) — ✅ ready: `https://al-tayabat.com/deletion`. This page was just rewritten (2026-07-12) to accurately describe the app's real self-service in-app deletion flow (`account.tsx` → `delete_user_account()` RPC, immediate, no waiting period) as the primary path, with the email request as a secondary option for users without the app.
   - Terms of service, if Play Console's store listing asks for one: `https://al-tayabat.com/terms`
   - **App content**: Data safety form (what data is collected — email, health goals/conditions, meal logs, ratings — and how it's used/shared), Content rating questionnaire, Target audience & content, Ads declaration (none if no ad SDK is integrated), Government apps / News apps declarations (both "No" almost certainly).
   - **Store listing**: short description (80 chars), full description (4000 chars), app icon (512×512, 32-bit PNG), feature graphic (1024×500), phone screenshots (min 2, recommend 4–8), category, contact email.

### ⚠️ New developer accounts — closed testing requirement
If this Play Console developer account is new (created after Nov 2023), Google requires a **closed testing track with 20+ opted-in testers active for 14 continuous days** before granting production access — this applies regardless of app quality and can't be skipped. Worth checking Play Console → your account's status now, since it directly affects how "fast" a first release can actually go out. If the account already has production access from before that policy, this doesn't apply.
